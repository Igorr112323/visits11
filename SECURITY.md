# Отчёт по безопасности и сборке — Visits11 (КубГАУ · Учёт посещаемости)

**Объект аудита:** репозиторий `Igorr112323/visits11`, ветка `arena/b2a4721c-visits11`
(состояние кода на коммит `25c982f`, 11.10.2026).

**Метод:** статический разбор исходного кода всех четырёх приложений (ПК WPF,
Android-преподаватель, Android-студент, iOS-студент). Динамический пентест на живых
устройствах, эмуляторах, фаззинг и анализ трафика **не проводились** — это
программный аудит кода, а не «испытания по ГОСТ/ФСТЭК».

**Главный вывод.** Ядро защиты от подделки посещаемости сделано правильно:
отметиться можно только физическим NFC-касанием, телефон каждого студента
привязывается к аккаунту, а «отметка за другого» подсвечивается преподавателю.
Однако система **не является «полностью офлайн без серверной части»** (см. раздел 0),
и на периферийных контурах есть уязвимости: телефон преподавателя и ПК принимают
соединения из сети без аутентификации по протоколу HTTP без шифрования, а Wi-Fi-фолбэк
передаёт логины и пароли в открытом виде.

**Итог по уровням риска:** 1 высокий, 4 средних, 3 низких — таблица в разделе 1.6.

## 0. Что в постановке задачи не подтвердилось

Эти пункты важно прочитать первыми: отчёт по безопасности, написанный «по описанию»,
а не по коду, гарантировал бы ложную безопасность.

| Утверждение в задании | Как на самом деле в коде |
|---|---|
| «Серверная часть `server.exe` полностью удалена» | `server.exe` никогда не существовал. Серверная часть — это HTTP-API **внутри ПК-программы**: `Services/PhoneServer.cs` слушает порты 8090–8099 (`TcpListener(IPAddress.Any, port)`, строка 64) |
| «Все данные хранятся локально на телефонах (Room/SQLite, CoreData/SQLite)» | На телефонах базы нет вообще. База `attendance.db` (SQLite) лежит рядом с exe на ПК. Телефоны хранят только логин/пароль: Android — `SharedPreferences`, iOS — `UserDefaults` |
| «Приложение не делает ни одного сетевого запроса» | Android-студент без NFC опрашивает ПК по HTTP (`/api/login`, `/api/qr`, `/api/ping`), телефон преподавателя держит HTTP-сервер (`ServerSocket`, порт 8090), ПК ходит на телефон по USB-тетерингу (это тоже TCP/IP). Интернет не используется — но сеть есть |
| «Android ↔ Android (NFC), Android → iPhone (NFC), iPhone → Android (NFC)» | Обмена «студент ↔ студент» нет. Есть один сценарий: **студент (считыватель) → телефон преподавателя (HCE-карта)**. iPhone физически не может быть HCE-картой — с iOS отметка возможна только как «iPhone читает телефон преподавателя» |
| «UUID создаётся при первой установке и не может быть изменён или скопирован на другое устройство» | Android: не UUID, а `Settings.Secure.ANDROID_ID` (строка 182 `MainActivity.java`). iOS: `UUID().uuidString` в `UserDefaults` (строки 19–20 `ContentView.swift`) — не в Keychain. Копируется и подменяется: аппаратной аттестации и подписей нет |
| «Защита от подмены: аппаратные ключи, криптографические подписи, `identifierForVendor`» | Ничего из перечисленного не используется. Защита — сравнение строки `DeviceId` в базе ПК |
| «Защита от повторов: одноразовые токены с временной меткой» | Одноразовость есть только у QR-кода переклички (~10 с). Токены сессий — **долгоживущие** («вечный вход»), хранятся в открытом виде в БД ПК и в настройках телефона |
| «Отметка возможна только при физическом касании, не упрощать» | Верно для NFC-пути. Но у Android-телефонов без NFC есть Wi-Fi-фолбэк с QR: там отметка возможна **без касания** (см. риск `R-1`) |
| «Ссылок на готовые файлы не существует, нужно собирать самому» | Готовые файлы публикуются автоматически: [релиз v1.0.0](https://github.com/Igorr112323/visits11/releases) — `KubGAU-Journal.exe`, `KubGAU-Teacher.apk`, `KubGAU-Student.apk`, `Visits11-Student-iOS-unsigned.ipa`. Сборка из исходников — в `BUILD.md` |

## 1. Безопасность

### 1.1 Уникальная идентификация устройства

| Платформа | Что используется | Где хранится | Особенности |
|---|---|---|---|
| Android (студент) | `Settings.Secure.ANDROID_ID` | системное значение | Не UUID и не генерируется приложением. Меняется при сбросе к заводским настройкам **по документированному поведению**; может быть подменён на root-устройстве или в эмуляторе |
| iOS (студент) | `UUID().uuidString`, генерируется приложением при первом входе | `UserDefaults`, ключ `device` | `UserDefaults` — не защищённое хранилище: удаляется при переустановке приложения, читается и правится на джейлбрейке. `identifierForVendor` (как в задании) не используется |

Что это даёт: у каждого телефона есть довольно устойчивый строковый идентификатор,
по которому ПК отличает «свой» телефон от «чужого».

Чего это **не** даёт:
- идентификатор не подписан устройством и никак не подтверждается аппаратно —
  на телефоне с root это обычная строка, которую можно скопировать в другое устройство;
- на iOS идентификатор лежит в незащищённом хранилище и теряется при переустановке
  (после чего аккаунт считается «привязанным к другому телефону» — это защита,
  но не починка);
- «не может быть изменён или скопирован на другое устройство» — **неверно**:
  копирование возможно, защита строится только на том, что обычный студент этого не делает.

### 1.2 Защита от подмены (spoofing)

Реализована как **привязка аккаунта к первому телефону** — строковое сравнение в базе ПК:

- вход студента (`LessonViewModel.LoginInternal`): пароль сверяется с базой, затем
  проверяется, не принадлежит ли этот `device` другому студенту, и совпадает ли он
  с сохранённым `DeviceId`; при первом входе — привязка `SetDeviceId`;
- отметка (`LessonViewModel.MarkStudentInternal`): те же проверки; при несовпадении —
  отказ с кодом `5` («аккаунт привязан к другому телефону»);
- «телефон другого студента использовали для отметки за него» → `FlagSuspicious`
  подсвечивает строку настоящего владельца меткой «⚠ Что-то не так»
  и показывает преподавателю всплывающее уведомление.

Ограничения (важно для честного отчёта):
- никакой криптографической подписи в обмене нет: и NFC-обмен (`APDU INS 0x10`),
  и HTTP-запросы передают `DeviceId` как обычное поле, которое клиент выбирает сам;
- аппаратной аттестации устройства (Play Integrity / SafetyNet, DeviceCheck / App Attest)
  нет — то есть проверяется «какой идентификатор назвался», а не «настоящее ли это устройство»;
- метка «Что-то не так» живёт только в модели текущей переклички (`row.Suspicious`)
  и в базу/журнал не сохраняется — после окончания занятия след попытки теряется.

Эксплуатация (в теории): получив root/jailbreak и скопировав `DeviceId` и токен
однокурсника, можно отметиться с его аккаунта; система это не заметит, потому что
признаков подмены, кроме совпадения строки, у неё нет.

### 1.3 Криптография: что есть и чего нет

**Есть:**

| Механизм | Реализация |
|---|---|
| Токен сессии | 128 бит из `RandomNumberGenerator` (`PhoneServer.cs:451`) — стойкий |
| Пароли студентов | 10 символов из алфавита 32 (без `0/O/1/I`), `RandomNumberGenerator` (`AuthService.cs:85`) — ~50 бит, перебор нереален |
| QR-код переклички (Wi-Fi-фолбэк) | AES-256-CBC, ключ новый на каждую перекличку, внутри `[магия][id переклички][id студента][5-секундное окно][нонс]` (`LessonViewModel.cs:157–232`) |
| CRC32 в личном QR-коде студента | Только контроль целостности (защита от кривого распознавания картинки), **не** подпись |

**Нет (то есть в отчёте нельзя писать, что это есть):**

- TLS/HTTPS: оба Android-манифеста включают `android:usesCleartextTraffic="true"`,
  HTTP-серверы ПК и телефона преподавателя работают без шифрования;
- подписи/аутентификации HTTP-запросов (HMAC, клиентские сертификаты, общий секрет) —
  ни у ПК, ни у телефона преподавателя нет ни одного секрета, которым можно отличить
  «свой» клиент от чужого;
- хеширования паролей: столбец `Students.Password` хранит пароль в открытом виде,
  и он же в открытом виде лежит в QR-файле студента (обратимый base64);
- шифрования локального хранилища телефонов (EncryptedSharedPreferences, Keychain);
- одноразовости токенов сессий (см. 1.4).

### 1.4 Защита от повторного использования (replay)

| Контур | Есть ли защита | Как устроено |
|---|---|---|
| NFC-касание (основной путь) | Частично | Касания обрабатываются по одному (`TAP_LOCK`), ответ привязан к номеру запроса (`id`), ожидание ≤ 4 с. Повторно «проиграть» перехваченный NFC-обмен без считывателя и без совпадающего `DeviceId` нельзя |
| QR-код переклички (скриншот) | Да | Живёт ~10 секунд (текущее окно 5 с ± предыдущее), ключ свой на каждую перекличку, внутри id переклички и нонс — скриншот бесполезен |
| Личный QR-код входа из галереи | Нет | Постоянный, не истекает; это умышленно (файл выдаётся один раз на семестр) |
| Токен сессии | Нет | Токен «вечный»: он не истекает, не одноразовый и хранится в открытом виде в БД (таблица `Sessions`) и на телефоне |
| Wi-Fi-фолбэк отметки | Нет | `POST /api/nfc_mark {token, device}` не содержит ни метки времени, ни нонса: перехваченный запрос можно повторить сколько угодно раз |

### 1.5 Физическая безопасность (NFC)

**NFC-путь подтверждается:** отметка происходит внутри NFC-сеанса, который физически
теряется при отрыве телефонов (IsoDep, таймаут 5 с; телефон преподавателя ждёт ответ
ПК ≤ 4 с). Удалённо «приложить» телефон к другому телефону через интернет невозможно.

**Но есть исключение, которое нельзя замалчивать:** у Android-телефонов **без NFC**
приложение студента работает через Wi-Fi — показывает QR, который ПК генерирует
каждые 5 секунд. Там физический контакт не требуется: достаточно находиться в той же
сети и получить/перехватить токен сессии (риск `R-1`). Для iPhone и для телефонов
с NFC путь один — касание.

### 1.7 Что делать в первую очередь

1. **Закрыть телефон преподавателя от сети** (`R-1`) — самое дешёвое и самое важное:
   слушать только USB-адрес и/или требовать общий секрет в заголовке запроса.
2. **Wi-Fi-фолбэк — выключить по умолчанию** (`R-2`, `R-3`): NFC-путь покрывает
   все современные телефоны, а фолбэк сейчас — единственная дыра, через которую
   можно отметиться, не подходя к преподавателю.
3. **Хранить секреты на телефоне правильно** (`R-4`): Keychain на iOS,
   `EncryptedSharedPreferences` на Android, срок жизни токена.
4. **Сохранять следы нарушений** (`R-5`): писать метку «Что-то не так» в БД.
5. **Перейти на подписанные запросы**: при первом входе выдавать телефону секрет,
   дальше подписывать им каждое касание/отметку (HMAC + нонс + время) — это закрывает
   и перехват, и повторы, и подмену без аппаратной аттестации.

## 2. Архитектура (как есть)

```
        ПК «Журнал КубГАУ» (Windows, .NET 8 WPF)                 ┌──────────────────┐
  ┌───────────────────────────────────────────────┐              │ attendance.db    │
  │ JournalView / LessonView / StudentsView        │              │ (SQLite: группы, │
  │ DatabaseService  AuthService  WordService      │◄────────────►│  студенты,       │
  │ PhoneServer (8090–8099, IPAddress.Any)         │              │  занятия,        │
  │ CameraLink  (поиск телефона в сети)            │              │  отметки, токены)│
  └───────────────────────────────────────────────┘              └──────────────────┘
        ▲                                              ▲
        │ исходящие TCP-соединения                     │ HTTP без шифрования
        │ (USB-тетеринг: usb0/rndis0)                  │ (Wi-Fi, фолбэк)
        │ GET /info, /frame, /event, POST /event_result│ GET /api/qr, POST /api/nfc_mark
        ▼                                              │
  ┌───────────────────────────┐                        │
  │ Телефон преподавателя     │                        │
  │  MainActivity (HTTP 8090) │       NFC-касание     │
  │  TeacherCardService (HCE) │◄───────────────────────┼──────────┐
  └───────────────────────────┘                        │          │
                                                       │   ┌──────┴───────┐
                                                       │   │ Android-     │
                                                       │   │ студент      │
                                                       │   │ (считыватель)│
                                                       │   └──────────────┘
                                                       │   ┌──────────────┐
                                                       └───│ iPhone-      │
                                                           │ студент      │
                                                           │ (Core NFC)   │
                                                           └──────────────┘
```

**Три сетевых контура** (важно: «офлайн» здесь = «без интернета», а не «без сети»):

1. **ПК ↔ телефон преподавателя** — TCP-соединения по USB-тетерингу, инициирует ПК
   (брандмауэр Windows ничего не блокирует). По этому каналу идут кадры камеры
   (`/frame` — кадров больше нет, остался pacing), NFC-касания (`/event`) и ответы
   на них (`/event_result`).
2. **Телефон студента без NFC ↔ ПК** — HTTP по Wi-Fi: вход, получение PNG с QR
   переклички, отметка. Работает через камеру преподавателя (ПК распознаёт QR
   с кадров, которые получает с телефона преподавателя).
3. **Телефон преподавателя ↔ Wi-Fi** — телефон слушает порт 8090 на всех интерфейсах;
   именно это создаёт риск `R-1`.

**Что хранится где:**

| Данные | Где | В каком виде |
|---|---|---|
| Группы, студенты, логины/пароли, занятия, отметки, токены | `attendance.db` рядом с exe | SQLite, **без шифрования**; пароли — открытым текстом |
| Тема оформления | `settings.json` рядом с exe | JSON |
| Логин/пароль студента, токен, `DeviceId` | телефон студента | Android — `SharedPreferences`; iOS — `UserDefaults` |
| Собственной базы на телефоне | — | Нет ни на Android, ни на iOS |

**Что происходит без ПК:** ничего из отметок. Телефон преподавателя ждёт ответ от ПК
≤ 4 секунды и, не дождавшись, отвечает студенту кодом `4` («не получилось»);
на экране телефона преподавателя — «Нет связи с ПК». Это прямое следствие того,
что авторизация и база живут на ПК.

**Синхронизация данных** идёт не «исключительно через NFC»: NFC передаёт только
данные студента (`логин\nпароль\nDeviceId` или `токен\nDeviceId`, APDU INS `0x10`,
AID `F0391101020304`), а вся запись, проверка и хранение происходят на ПК по каналу
из пункта 1. Между телефонами студентов данные не передаются вообще.

## 3. Авторизация студента по QR-коду из галереи

**Как работает сейчас (реализовано в этой же ветке):**

1. Преподаватель: вкладка «Студенты» → **«Экспорт QR-кодов»** → папка
   «QR-коды <группа>»: PNG на каждого студента + «Как войти.txt».
2. Студент получает свою картинку, сохраняет её в галерею.
3. В приложении на экране входа — «Войти по QR из галереи»:
   - Android: системный выбор фото (`ACTION_PICK_IMAGES` / `ACTION_OPEN_DOCUMENT`,
     без разрешений на хранилище), распознавание ZXing (обычное и «негативное»),
     фоновая обработка, уменьшение больших снимков;
   - iOS: `PHPicker` (без разрешений и ключей `Info.plist`), распознавание системным
     `Vision` (`VNDetectBarcodesRequest`).
4. Разбор строки: префикс `V11S1`, четыре поля base64url (логин, пароль, ФИО),
   CRC32 от машинной строки — защита от чужой картинки и от кривого распознавания.
5. Логин и пароль сохраняются ровно так же, как при ручном вводе;
   дальше — обычная логика: NFC-касание (полный вход с привязкой устройства)
   или Wi-Fi-фолбэк.

**Что это даёт:** не нужно диктовать логин и пароль, нет камеры и разрешений,
работает полностью без сети и сервера.

**Чего это не даёт (для честности):** CRC32 — не подпись, а файл содержит логин и
пароль в обратимом виде, то есть QR-файл **равен паролю**: кто получил картинку —
может войти этим аккаунтом (но отметиться с чужого телефона не сможет — сработает
привязка `DeviceId`). Одноразовых/сгорающих кодов пока нет; формат к этому готов
(достаточно поднять версию до `V11S2` и дописать поля).

## 4. Чек-лист безопасности

Вопросы из задания — с честными ответами по коду, а не по замыслу.

| Проверка | Ответ | Почему |
|---|---|---|
| Студент не может отметиться, не приходя на пару? | **Частично** | NFC-путь: да, нужно касание. Wi-Fi-фолбэк (`R-2`, `R-3`): да, может — из коридора в той же сети, если добудет токен/QR |
| Скриншот QR-кода переклички работает? | **Нет** | AES-ключ свой на каждую перекличку, окно 5 с ±1, id переклички и нонс внутри |
| Личный QR-код входа можно передать другому? | **Да, но отметку это не даёт** | Файл = логин+пароль; привязка `DeviceId` не пустит чужой телефон |
| Можно ли отметиться за другого с чужого телефона? | **Нет** | Проверка `DeviceId` в `LoginInternal`/`MarkStudentInternal`, отказ с кодом `5` |
| Попытка «помочь кенту» заметна? | **Только на занятии** | `FlagSuspicious` рисует метку в текущем списке; в БД не сохраняется (`R-5`) |
| Уникальность устройства подтверждена аппаратно? | **Нет** | `ANDROID_ID` / UUID в `UserDefaults`, никакой аттестации (`R-4`) |
| Телефон можно клонировать? | **Да, с root/jailbreak** | `DeviceId` и токен — обычные строки в обычных хранилищах |
| Данные защищены при передаче? | **Нет, кроме NFC** | HTTP без TLS, `usesCleartextTraffic=true`, токен в query-строке (`R-2`) |
| Учётные данные защищены при хранении? | **Нет** | Пароли открытым текстом в SQLite и в QR; токены — в открытом виде (`R-4`, `R-6`) |
| Повтор запроса возможен? | **Да, на Wi-Fi-контуре** | Нет нонса/времени в `/api/nfc_mark`; токен вечный (`R-2`) |
| Телефон преподавателя защищён от чужих в сети? | **Нет** | HTTP-сервер на всех интерфейсах без аутентификации (`R-1`) |
| Интернет используется? | **Нет** | Ни одно устройство не обращается во внешнюю сеть; всё в локальной сети/по кабелю |
| Автоматическая подмена даты/времени помогает? | **Нет на NFC-пути** | Отметка ставится по времени ПК; окно QR считает ПК, а не телефон |

## 5. Как собрать и получить файлы

**Готовые файлы уже собраны** — их создаёт GitHub Actions при каждом изменении:

👉 **[Релиз v1.0.0](https://github.com/Igorr112323/visits11/releases)** — четыре файла:

| Файл | Что это |
|---|---|
| `KubGAU-Journal.exe` | ПК-программа преподавателя (Windows 10/11 x64, установка не нужна) |
| `KubGAU-Teacher.apk` | Телефон преподавателя (NFC-терминал) |
| `KubGAU-Student.apk` | Телефон студента (Android) |
| `Visits11-Student-iOS-unsigned.ipa` | iPhone-студент (подписывается своим Apple ID через Sideloadly) |

Локальная сборка из исходников — команды, пути к файлам и требования:
см. **`BUILD.md`**. Коротко:

```bash
# APK преподавателя и студента (нужны JDK 17, Gradle 8.9, Android SDK 34)
cd android && gradle assembleRelease
#   → app/build/outputs/apk/release/app-release.apk        (преподаватель)
#   → student/build/outputs/apk/release/student-release.apk (студент)

# EXE журнала (Windows, .NET 8 SDK)
dotnet publish -c Release -r win-x64 -p:PublishSingleFile=true \
  -p:SelfContained=true -p:IncludeNativeLibrariesForSelfExtract=true -o publish
#   → publish/Visits11.exe  → переименовать в KubGAU-Journal.exe

# IPA студента (macOS + Xcode + xcodegen)
brew install xcodegen && cd ios && xcodegen generate
xcodebuild -project Visits11Student.xcodeproj -scheme Visits11Student \
  -configuration Release -sdk iphoneos -derivedDataPath build \
  CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY="" build
#   → ios/build/Build/Products/Release-iphoneos/Visits11Student.app → упаковать в Payload/ → .ipa
```

Для установки на iPhone и распространения нужен Apple ID (для теста — бесплатная
подпись через Sideloadly, живёт 7 дней) или Apple Developer Account ($99/год).
