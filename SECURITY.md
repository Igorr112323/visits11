# Отчёт по безопасности — Visits11 (КубГАУ · Учёт посещаемости)

**Объект аудита:** репозиторий `Igorr112323/visits11`, ветка `arena/b2a4721c-visits11`,
версия без логинов и паролей (вход студента — только по QR-коду; работа без интернета
и без Wi-Fi, связь ПК с телефоном преподавателя — по USB-кабелю).

**Метод:** статический разбор исходного кода всех четырёх приложений (ПК WPF,
Android-преподаватель, Android-студент, iOS-студент). Динамический пентест на живых
устройствах, эмуляторах, фаззинг и анализ трафика **не проводились** — это
программный аудит кода, а не «испытания по ГОСТ/ФСТЭК».

**Главный вывод.** Ядро защиты от подделки посещаемости сделано правильно: отметиться
можно только физическим NFC-касанием, телефон каждого студента привязывается к аккаунту,
а «отметка за другого» подсвечивается преподавателю. После перехода на вход по QR-коду
исчезли два самых грубых дефекта прошлой версии: учётных данных (логинов/паролей) в системе
больше нет вовсе, а обе программы-телефона и ПК работают без Wi-Fi — телефон преподавателя
слушает **только адрес USB-интерфейса**, у приложения студента нет даже разрешения
`INTERNET`.

**Итог по уровням риска:** 0 высоких, 3 средних, 4 низких — таблица в разделе 1.6.
Остаточные риски — это перехват трафика USB-канала, отсутствие аппаратной аттестации
устройства и незащищённое хранение кода студента в настройках телефона.

## 0. Проверка утверждений о системе (по коду, а не по описанию)

Отчёт по безопасности, написанный «по описанию», гарантирует ложную безопасность,
поэтому каждое утверждение о системе сверялось с кодом.

| Утверждение | Как на самом деле в коде |
|---|---|
| «Логинов и паролей нет» | **Верно.** Столбцов `Login`/`Password` в базе нет (`Services/DatabaseService.cs`, таблица `Students`), генераторов `GenerateLogin`/`GeneratePassword` — тоже (`Services/AuthService.cs`), экспорт студентов в Word с логином и паролем удалён (`Services/WordService.cs`). В QR-коде студента лежат только код (128 бит) и ФИО (`Services/StudentQr.cs`) |
| «Все данные хранятся локально» | **Верно.** База `attendance.db` (SQLite) — рядом с exe; собственных баз у телефонов нет. На телефонах лежит только код студента: Android — `SharedPreferences`, iOS — `UserDefaults` |
| «Приложение не делает ни одного сетевого запроса» | **Верно для приложений студентов.** В манифесте Android-студента нет разрешения `INTERNET` (`android/student/src/main/AndroidManifest.xml`), сокетов в коде нет; iOS-приложение не делает сетевых запросов вообще. Телефон преподавателя держит HTTP-сервер, но **только на адресе USB-интерфейса**: `new ServerSocket(SERVER_PORT, 8, usbAddress())` (`android/app/.../MainActivity.java:215`), пока кабеля нет — не слушает ничего. ПК сам, исходящими соединениями, забирает касания у телефона преподавателя по USB (`Services/PhoneLink.cs`). Интернет не используется нигде |
| «Отметка возможна только при физическом касании» | **Верно.** Wi-Fi-фолбэк с QR-кодом переклички удалён: в ПК-программе нет ни сервера для телефонов, ни распознавания кадров камеры (`Services/PhoneServer.cs`, `CameraLink.cs`, `QrScanner.cs` удалены). Отметка ставится только внутри NFC-сеанса |
| «Серверная часть удалена» | `server.exe` никогда не существовал — серверной части в системе и не было, всё выполняется в четырёх приложениях. Прежний HTTP-API внутри ПК-программы (`PhoneServer.cs`) в этой версии удалён |
| «Обмен iPhone ↔ Android по Bluetooth/NFS» | Такого в системе нет и не было. Единственный канал между телефонами — **NFC-касание**: телефон студента (считыватель) → телефон преподавателя (HCE-карта). Bluetooth и NFS в коде отсутствуют |
| «Android ↔ Android (NFC), Android → iPhone, iPhone → Android» | Обмена «студент ↔ студент» нет. iPhone физически не может быть HCE-картой, поэтому сценарий один для всех: **студент читает телефон преподавателя** |
| «UUID создаётся при установке и не может быть изменён или скопирован» | Android: не UUID, а `Settings.Secure.ANDROID_ID` (`android/student/.../MainActivity.java:167`). iOS: `UUID().uuidString` в `UserDefaults` (строки 17–21 `ios/Sources/ContentView.swift`) — не в Keychain. Копируется и подменяется: аппаратной аттестации нет |
| «Аппаратные ключи, криптоподписи, одноразовые токены» | Ничего из перечисленного не используется и не заявляется. Защита — сравнение строки `DeviceId` в базе ПК и постоянный (не сгорающий) код студента |
| «Ссылок на готовые файлы не существует, нужно собирать самому» | Готовые файлы публикуются автоматически: [релиз v1.0.0](https://github.com/Igorr112323/visits11/releases) — `KubGAU-Journal.exe`, `KubGAU-Teacher.apk`, `KubGAU-Student.apk`, `Visits11-Student-iOS-unsigned.ipa`. Сборка из исходников — в `BUILD.md` |

## 1. Безопасность

### 1.1 Что служит «пропуском» и «удостоверением»

| Платформа | Чем входит студент | Чем подтверждается телефон |
|---|---|---|
| Android | Код студента из QR-кода (`QrToken`, 128 бит случайности) | `Settings.Secure.ANDROID_ID` — отправляется при касании вместе с кодом |
| iOS | Тот же код из того же QR-кода | `UUID().uuidString`, генерируется приложением и хранится в `UserDefaults`, ключ `device` |

Что это даёт: студент входит одним движением (камера или картинка из галереи), не
запоминая ничего; у каждого телефона есть устойчивый строковый идентификатор, по которому
ПК отличает «свой» телефон от чужого.

Чего это **не** даёт:
- идентификатор не подписан устройством и не подтверждается аппаратно — на телефоне
  с root это обычная строка, которую можно скопировать в другое устройство;
- на iOS идентификатор лежит в незащищённом хранилище и теряется при переустановке
  (после чего приложение ответит «этот телефон привязан к другому студенту»);
- «не может быть изменён или скопирован» — **неверно**: копирование возможно, защита
  строится только на том, что обычный студент этого не делает.

### 1.2 Защита от подмены (spoofing)

Реализована как **привязка аккаунта к первому телефону** — строковое сравнение в базе ПК
(`ViewModels/LessonViewModel.cs`):

- касание (`HandleNfcRequest`): студент ищется в базе по коду из QR
  (`FindByQrToken`, строка 117); при первом касании телефон привязывается к студенту,
  при следующем — `DeviceId` сверяется с сохранённым;
- «телефон другого студента использовали для отметки за него» → отказ с кодом `5`
  («телефон привязан к другому студенту») **и** метка «⚠ Что-то не так» в строке
  настоящего владельца телефона (`FlagSuspicious`, строки 176–183);
- незнакомый код, которого нет в базе, → код `2` («кода нет в журнале»), телефон
  студента при этом стирает у себя недействительный код и просит войти заново.

Ограничения (важно для честного отчёта):
- криптографической подписи в обмене нет: и NFC-обмен (APDU INS `0x10`), и HTTP-запросы
  передают `DeviceId` как обычное поле, которое клиент выбирает сам;
- аппаратной аттестации устройства (Play Integrity / SafetyNet, DeviceCheck / App Attest)
  нет — проверяется «какой идентификатор назвался», а не «настоящее ли это устройство»;
- метка «Что-то не так» живёт только в модели текущей переклички (`row.Suspicious`)
  и в базу не сохраняется (риск `R-5`).

### 1.3 Криптография: что есть и чего нет

**Есть:**

| Механизм | Реализация |
|---|---|
| Код студента для QR | 128 бит из `RandomNumberGenerator` (`Services/AuthService.cs:49–52`) — перебор нереален |
| Номер запроса на касание | Каждое касание получает свой `id`; ответ ПК адресован конкретному запросу (`LessonViewModel.Reply`) — перепутать ответы двух студентов нельзя |
| CRC32 в QR-коде студента | Только контроль целостности (защита от чужой картинки и кривого распознавания), **не** подпись (`Services/StudentQr.cs`) |
| Самопроверка при экспорте | ПК перед сохранением картинки разбирает свой же код обратно; при расхождении экспорт останавливается с ошибкой (`Services/QrExportService.cs`) |

**Нет (то есть в отчёте нельзя писать, что это есть):**

- TLS/HTTPS и шифрования канала USB: обмен с телефоном преподавателя — обычный HTTP
  по USB-сети (`192.168.42.x`), без шифрования и без общего секрета;
- аутентификации запросов между ПК и телефоном преподавателя (HMAC, клиентские
  сертификаты, общий секрет) — ни у ПК, ни у телефона нет секрета, которым можно
  отличить «своё» соединение от чужого;
- аппаратной аттестации устройства;
- шифрования локальных хранилищ (EncryptedSharedPreferences, Keychain);
- одноразовости кода студента: код постоянный (это осознанное решение — файл выдаётся
  один раз на семестр).

### 1.4 Защита от повторного использования (replay)

| Контур | Есть ли защита | Как устроено |
|---|---|---|
| NFC-касание | Да, практически | Обмен идёт внутри NFC-сеанса, который физически теряется при отрыве телефонов (IsoDep, таймаут 5 с). Касания обрабатываются по одному, ответ привязан к номеру запроса (`id`). «Проиграть» перехваченный обмен без считывателя и без совпадающего `DeviceId` нельзя |
| QR-код студента | Нет, и это умышленно | Постоянный, не истекает. Второй экземпляр картинки бесполезен: аккаунт привязан к первому телефону |
| Повтор касания одним и тем же студентом | Не мешает | Повторная отметка того же студента на том же занятии — не ошибка, отметка идемпотентна |

### 1.5 Физическая безопасность (NFC)

**Подтверждается:** отметка происходит внутри NFC-сеанса, который обрывается при отрыве
телефонов (IsoDep, таймаут 5 с; телефон преподавателя ждёт ответ ПК ≤ 4 с, чтобы уложиться).
Удалённо «приложить» телефон к другому телефону через интернет невозможно.

**Исключений больше нет.** В прошлой версии у Android-телефонов без NFC работал Wi-Fi-фолбэк
(QR-код переклички), где касание не требовалось. В этой версии такого пути нет: на ПК нет
ни сервера для телефонов, ни распознавания кадров камеры, а в приложении студента нет ни
сокетов, ни разрешения `INTERNET`. Телефон студента без NFC отметиться не может —
только вручную, преподавателем в журнале.

### 1.6 Найденные слабые места

| ID | Уровень | Что не так | Где | Что это позволяет | Что делать |
|---|---|---|---|---|---|
| `R-1` | Средний | Канал ПК ↔ телефон преподавателя — HTTP без шифрования и без общего секрета; ПК принимает ответ на касание от того, кто первым ответит на его запрос | `Services/PhoneLink.cs`, `android/app/.../MainActivity.java` | Кто получил доступ к USB-сети телефона (или запустил на ПК программу-обманку) может видеть код и `DeviceId` студента в момент касания | Ввести общий секрет (HMAC на запросы) или перейти на HTTPS с самоподписанным сертификатом и пиннингом |
| `R-2` | Средний | Код студента хранится в открытом виде: `Students.QrToken` в SQLite ПК и в настройках телефона (`SharedPreferences`/`UserDefaults`) | `Services/DatabaseService.cs`, оба приложения студента | Копия файла базы или root/jailbreak телефона = доступ к аккаунту (но отметиться с чужого телефона всё равно не выйдет — сработает привязка `DeviceId`) | Хранить код в Keychain/EncryptedSharedPreferences; на ПК шифровать БД паролем преподавателя |
| `R-3` | Средний | Метка «⚠ Что-то не так» не сохраняется в базу — только в модель текущего занятия (`row.Suspicious`, строка 181) | `ViewModels/LessonViewModel.cs` | Попытка отметиться за другого исчезает после окончания занятия: доказательств у преподавателя не остаётся | Сохранять признак в `Attendance`/отдельную таблицу и показывать в журнале |
| `R-4` | Низкий | Нет аппаратной аттестации устройства: идентификатор — обычная строка, которую на root/jailbreak можно скопировать | оба приложения студента | Клонирование телефона вместе с кодом и `DeviceId` неотличимо от настоящего устройства | Подписывать запросы ключом, созданным в защищённом хранилище телефона (Android Keystore / Secure Enclave) |
| `R-5` | Низкий | Проверка «наш» телефон идёт по адресу-подписи `GET /info` → `{"app":"visits11-teacher"}` — подпись легко подделать | `Services/PhoneLink.cs`, `android/app/.../MainActivity.java:262–264` | Программа-обманка, запущенная на ПК/в USB-сети, может выдать себя за телефон преподавателя | Тот же общий секрет, что в `R-1` |
| `R-6` | Низкий | На ПК нет ограничения на число попыток и нет журнала событий безопасности: неудачные касания видит только преподаватель на экране | `Services/PhoneLink.cs`, `ViewModels/LessonViewModel.cs` | Серия попыток «перебрать код» на паре останется незамеченной, если преподаватель не смотрит на экран | Писать неудачные касания в журнал/файл рядом с exe |
| `R-7` | Низкий | База `attendance.db` и `settings.json` лежат рядом с exe без шифрования | `Services/DatabaseService.cs` | Копия папки с программой = копия журнала посещаемости и кодов студентов | Шифровать базу (SQLCipher) или хотя бы ограничить доступ к папке на уровне ОС |

Отдельно отмечаю, что **само действие проверки NIC-адресов ограничено**: ПК ищет телефон
преподавателя только среди адресов USB-модема (адаптер Ethernet с пометкой
`RNDIS/USB/tether`), Wi-Fi и обычный Ethernet пропускаются (`PhoneLink.BuildTargets`) —
посторонние адреса в сети не опрашиваются.

### 1.7 Что делать в первую очередь

1. **Закрыть канал ПК ↔ телефон** (`R-1`, `R-5`): при первой связке выдать телефону общий
   секрет и подписывать им запросы `GET /event` и `POST /event_result` (HMAC + нонс).
   Это закрывает и прослушивание, и обманку.
2. **Защитить хранение кода студента** (`R-2`): Keychain на iOS,
   `EncryptedSharedPreferences` на Android.
3. **Сохранять следы нарушений** (`R-3`) и неудачных касаний (`R-6`): писать метку
   «Что-то не так» и причину отказа в БД, показывать в журнале.
4. **Поднять планку подмены устройства** (`R-4`): ключ в Keystore/Secure Enclave,
   подпись каждого касания.

## 2. Архитектура (как есть)

```
        ПК «Журнал КубГАУ» (Windows, .NET 8 WPF)              ┌──────────────────┐
  ┌───────────────────────────────────────────────┐            │ attendance.db    │
  │ JournalView / LessonView / StudentsView        │            │ (SQLite: группы, │
  │ DatabaseService  AuthService  WordService      │◄──────────►│  студенты, коды, │
  │ QrExportService   StudentQr                    │            │  занятия, отметки)│
  │ PhoneLink (исходящие соединения, USB-модем)     │            └──────────────────┘
  └───────────────────────────────────────────────┘
        │                                              ▲
        │ GET /info, GET /event (long-poll),           │ ничего: у приложений
        │ POST /event_result — только USB-канал        │ студентов нет сети
        ▼                                              │
  ┌───────────────────────────┐                        │
  │ Телефон преподавателя     │        NFC-касание     │
  │  MainActivity (8090, но   │◄───────────────────────┼──────────┐
  │  только адрес USB)        │                        │          │
  │  TeacherCardService (HCE) │                        │   ┌──────┴───────┐
  └───────────────────────────┘                        │   │ Android-     │
                                                       │   │ студент      │
                                                       │   │ (считыватель)│
                                                       │   └──────────────┘
                                                       │   ┌──────────────┐
                                                       └───│ iPhone-      │
                                                           │ студент      │
                                                           │ (Core NFC)   │
                                                           └──────────────┘
```

**Один сетевой контур** (важно: «офлайн» в описании задачи = «без интернета», и в этой
версии система действительно обходится без внешней сети и без Wi-Fi):

1. **ПК ↔ телефон преподавателя** — TCP-соединения по USB-кабелю (режим «USB-модем»),
   инициирует ПК, поэтому брандмауэр Windows ничего не блокирует. По этому каналу идут
   NFC-касания (`GET /event`) и ответы на них (`POST /event_result`).
2. **Телефон преподавателя ↔ Wi-Fi** — связи нет: сервер слушает исключительно адрес
   USB-интерфейса (`MainActivity.java:215`), пока кабель не подключён — не слушает ничего.
3. **Телефоны студентов** — сети нет вовсе: на Android нет разрешения `INTERNET` и нет
   сокетов в коде, на iOS нет ни одного сетевого вызова. Общение с миром — только NFC
   и QR-код.

**Что хранится где:**

| Данные | Где | В каком виде |
|---|---|---|
| Группы, студенты, коды студента, занятия, отметки | `attendance.db` рядом с exe | SQLite, **без шифрования** (`R-7`) |
| Тема оформления | `settings.json` рядом с exe | JSON |
| Код студента и `DeviceId` | телефон студента | Android — `SharedPreferences`; iOS — `UserDefaults` (`R-2`) |
| Логины и пароли | — | **Нигде: их в системе нет** |
| Собственной базы на телефоне | — | Нет ни на Android, ни на iOS |

**Что происходит без ПК:** ничего из отметок. Телефон преподавателя ждёт ответ ПК
≤ 4 секунды и, не дождавшись, отвечает студенту кодом `4` («не получилось»); на экране
телефона преподавателя — «Нет связи с ПК». Это прямое следствие того, что проверка
и запись живут на ПК.

**Синхронизация данных** идёт не «исключительно через NFC»: NFC передаёт только данные
студента (`код\nDeviceId`, APDU INS `0x10`, AID `F0391101020304`), а вся запись, проверка
и хранение происходят на ПК по каналу USB. Между телефонами студентов данные не передаются
вообще.

## 3. Вход студента по QR-коду — и почему логин с паролем больше не нужны

**Как работает сейчас:**

1. Преподаватель: вкладка «Студенты» → **«Экспорт QR-кодов»** → папка
   «QR-коды <группа>»: PNG на каждого студента + «Как войти.txt» с инструкцией.
   Там же напротив каждого студента есть кнопка **«QR-код»** — показать картинку
   на экране и сохранить её в файл.
2. Студент получает свою картинку (файл или снимок экрана ПК).
3. В приложении на экране входа — ровно два способа, других нет:
   - **«Сканировать QR-код»**: Android — камера через `IntentIntegrator`; iOS — камера
     через `AVFoundation` (`CameraScanner.swift`);
   - **«Загрузить из галереи»**: Android — системный выбор фото
     (`ACTION_PICK_IMAGES` / `ACTION_OPEN_DOCUMENT`, без разрешений на хранилище),
     распознавание ZXing (обычное и «негативное»); iOS — `PHPicker` (без разрешений
     и ключей `Info.plist`) и системный `Vision` (`VNDetectBarcodesRequest`).
4. Разбор строки: префикс `V11S2`, поля base64url (код, ФИО) и CRC32 от машинной строки —
   защита от чужой картинки и от кривого распознавания. Один и тот же разбор на всех
   трёх платформах: `Services/StudentQr.cs`, `android/student/.../MainActivity.java`,
   `ios/Sources/QrLogin.swift`.
5. Код и ФИО сохраняются в настройках телефона; дальше — NFC-касание
   (проверка кода в базе ПК + привязка устройства).
   Переключиться на другого студента можно долгим нажатием по статусу (выход).

**Что это даёт:** ничего не нужно диктовать и запоминать, вход работает полностью
без сети и без сервера, QR-код — единственный «ключ доступа».

**Чего это не даёт (для честности):** CRC32 — не подпись, а код в QR-коде лежит
в обратимом виде, то есть **картинка равна коду студента**: кто получил чужой PNG,
может войти этим аккаунтом на своём телефоне. Отметку это не даёт (привязка `DeviceId`
не пустит чужой телефон), но формально доступ к аккаунту получить можно — см. `R-2`.
Одноразовых/сгорающих кодов нет; формат к этому готов (достаточно поднять версию
до `V11S3` и дописать поля).

## 4. Чек-лист безопасности

Вопросы — с честными ответами по коду, а не по замыслу.

| Проверка | Ответ | Почему |
|---|---|---|
| Студент не может отметиться, не приходя на пару? | **Да** | Отметка ставится только внутри NFC-сеанса; Wi-Fi-пути («отметиться из коридора») в системе больше нет |
| Скриншот QR-кода переклички работает? | **Неприменимо** | QR-кода переклички в этой версии нет — он был частью удалённого Wi-Fi-фолбэка |
| Личный QR-код можно передать другому? | **Да, но отметку это не даёт** | Картинка = код студента; чужой телефон отклонится привязкой `DeviceId` (код `5`) |
| Можно ли отметиться за другого с чужого телефона? | **Нет** | Проверка `DeviceId` в `LessonViewModel.HandleNfcRequest`, отказ с кодом `5` |
| Попытка «помочь кенту» заметна? | **Только на занятии** | `FlagSuspicious` рисует метку в текущем списке; в БД не сохраняется (`R-3`) |
| Уникальность устройства подтверждена аппаратно? | **Нет** | `ANDROID_ID` / UUID в `UserDefaults`, никакой аттестации (`R-4`) |
| Телефон можно клонировать? | **Да, с root/jailbreak** | Код и `DeviceId` — обычные строки в обычных хранилищах |
| Данные защищены при передаче? | **Только на NFC-контуре** | Касание идёт внутри физического NFC-сеанса; служебный HTTP по USB без шифрования (`R-1`) |
| Учётные данные защищены при хранении? | **Нет** | Код студента открытым текстом в SQLite и в настройках телефона (`R-2`); паролей в системе нет |
| Повтор запроса возможен? | **Нет на NFC-пути** | Обмен живёт только внутри касания; переиграть его без считывателя и `DeviceId` нельзя |
| Телефон преподавателя защищён от чужих в сети? | **Да, от Wi-Fi — полностью** | Сервер слушает только адрес USB-интерфейса (`MainActivity.java:215`); из Wi-Fi он недоступен, без кабеля не слушает ничего |
| Интернет используется? | **Нет** | Ни одно устройство не обращается во внешнюю сеть; у приложения студента нет даже разрешения `INTERNET` |
| Автоматическая подмена даты/времени помогает? | **Нет** | Отметка ставится по времени ПК, телефон в отметке времени не участвует |

## 5. Как собрать и получить файлы

**Готовые файлы уже собраны** — их создаёт GitHub Actions при каждом изменении:

👉 **[Релиз v1.0.0](https://github.com/Igorr112323/visits11/releases)** — четыре файла:

| Файл | Что это |
|---|---|
| `KubGAU-Journal.exe` | ПК-программа преподавателя (Windows 10/11 x64, установка не нужна) |
| `KubGAU-Teacher.apk` | Телефон преподавателя (NFC-терминал, связь с ПК по USB-кабелю) |
| `KubGAU-Student.apk` | Телефон студента (Android) |
| `Visits11-Student-iOS-unsigned.ipa` | iPhone-студент (подписывается своим Apple ID через Sideloadly) |

Локальная сборка из исходников — команды, пути к файлам и требования:
см. **`BUILD.md`**. Коротко:

```bash
# APK преподавателя и студента (нужны JDK 17, Gradle 8.9, Android SDK 34)
cd android && gradle assembleRelease
#   → app/build/outputs/apk/release/app-release.apk        (преподаватель)
#   → student/build/outputs/apk/release/student-release.apk (студент)

# EXE журнала (Windows, .NET 8 SDK)
dotnet publish -c Release -r win-x64 -p:PublishSingleFile=true \
  -p:SelfContained=true -p:IncludeNativeLibrariesForSelfExtract=true -o publish
#   → publish/Visits11.exe  → переименовать в KubGAU-Journal.exe

# IPA студента (macOS + Xcode + xcodegen)
brew install xcodegen && cd ios && xcodegen generate
xcodebuild -project Visits11Student.xcodeproj -scheme Visits11Student \
  -configuration Release -sdk iphoneos -derivedDataPath build \
  CODE_SIGNING_ALLOWED=NO CODE_SIGNING_REQUIRED=NO CODE_SIGN_IDENTITY="" build
#   → ios/build/Build/Products/Release-iphoneos/Visits11Student.app → упаковать в Payload/ → .ipa
```

Для установки на iPhone и распространения нужен Apple ID (для теста — бесплатная
подпись через Sideloadly, живёт 7 дней) или Apple Developer Account ($99/год).
